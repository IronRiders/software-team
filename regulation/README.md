# Rules and Regulations

One of the major problems the software department has faced in the past is regulation. We've had issues with branch permissions, what branch to use, what formatting to use, what architecture to use, and more. These problems are tedious and can lead to the blame game when things go wrong- which is especially bad during competition, in which these issues can make or break our score.

This document and its child documents are made specifically to help with this problem. I'll try to explain practically everything we do and why.

Please know: this is a living document. Just like any other of our repositories, you can propose changes- which is especially important to remember with these regulations. Want something changed? Make a pull request, or talk to the current software lead!

### Formatting

Formatting covers code format. We like to have some (fairly simple) formatting guidelines to keep things neat and readable in our code. You don't really need to consider formatting too much, because you can just use VSCode's handy-dandy "Format Code" feature (and the "Organize Imports" feature too).

Head [here](./format.md) for more.

### Architecture

If formatting is standardization of style, architecture is standardization of code structure. We use a command-based structure provided by WPILib, which you hopefully learned about during curriculum (check [this](curriculum/wpilib/week-1-system-structure.md) for more info). We use mostly standard guidelines for commands and subsystems, but there are a handful of things you should know about.

Head [here](./architecture.md) for more.

### Git and Github

You're using git right now! You probably already know the basics of how it works (if not take a look [here](../curriculum/tools/README.md)). We have a few rules to handle git permissions and branching. If you're going to be doing any work on the robot you will need to know these guidelines, _especially_ if you're going to work on it during competitions.

Head [here](./git-and-github.md) for more.
